---

## 1. 目的

评估并证明一套**开发者/测试工作流**，让后续实施与审查期间可以交互式地安装、重载、检查扩展运行时，而不改动任何产品语义。

## 2. 评估范围

1. **官方 Chrome 扩展开发指引 / skill**（若可用）：manifest、权限、service worker 生命周期的官方口径。
2. **`modern-web-guidance` 一类现代 Web 工程指引**（若相关）：构建、调试与测试组织。
3. **Chrome DevTools MCP 扩展专用工具**（受支持的前提下）：popup / content script / service worker 的运行时检查。
4. **隔离的 Chrome 开发/测试 profile**：与用户日常 profile 分离，避免污染真实数据。
5. **扩展安装 / 重载 / 检查工作流**：加载已构建 `dist/`、重载、查看控制台与错误。
6. **与既有确定性 E2E 的兼容性**：`e2e-verify.cjs` + Chrome for Testing 153 必须继续作为回归门。

## 3. 硬约束（不得违反）

1. **这是工具，不是产品行为**：不得为了让工具好用而修改产品语义、UI 契约、持久化或领域模型。
2. **不得替换既有确定性 E2E**。二者互补：
   - **仓库 E2E（`e2e-verify.cjs`）＝ 确定性回归门**（每次提交必须全绿）；
   - **DevTools MCP ＝ 交互式/运行时调查与验证**（人工或代理驱动的问题定位与确认）。
3. **不得引入产品代码变更**作为本 SPIKE 的产出；产出是**结论 + 可选的工具配置说明**。
4. **不得把个人环境配置写入仓库权威**（`RULES.md` / 规格 / `AGENTS.md` 的产品规则部分）。
5. **不得安装与当前范围无关的基础设施**；不得改动 CI、密钥、远端配置。
6. **隐私**：开发/测试 profile 中不得导入用户真实 profile 数据；`R-MIG-8` 的真实 profile 备份仍按其自身规则执行。

## 4. 产出（完成时）

- 一份结论：推荐 / 不推荐，以及推荐组合（哪些纳入日常、哪些仅临时使用）；
- 隔离 profile 的建立与复用步骤（可复现命令）；
- 扩展 install / reload / inspect 的标准操作序列；
- 与 `e2e-verify.cjs` 的边界说明（什么走 E2E、什么走 MCP）；
- 风险与不做什么（明确列出被否决的项）。

## 5. 验收（SPIKE 自身）

- 能在隔离 profile 中加载已构建扩展并完成一次完整用户路径（阅读标注 → 查询 → 标记 → 生词本 → 测评）；
- `e2e-verify.cjs` 在**未改动**的前提下仍 `E2E ALL PASS`；
- 结论文档明确「未修改任何产品代码」（如有产品代码改动，视为 SPIKE 越界，须回退）。
