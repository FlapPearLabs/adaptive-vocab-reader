# 词典路线对比：可审计广覆盖核心词典，还是高频核心包＋本地模型兜底？

**日期：** 2026-07-17
**状态：** 只读研究笔记，不修改 `RULES.md`，不冻结产品规则、技术选型或数值阈值。文中 100–300／180 或 240 条是早期样本量研究建议；当前已确认执行口径已改为“先冻结 Codex→Hermes→Reasonix Harness → 第一阶段总计 500 条，前 100 条为其中的合同门 → 每 100 条反思并沉淀候选 Skill”，以 `RULES.md` 为准。
**问题：** 当前的浏览器词汇学习插件，是否存在一份可直接对应“表达＋当前粗义项＋简中短释义＋离线＋可追溯”的专用词典？若不存在，比较两条数据路线：

- **路线 A：可审计的广覆盖核心词典。** 由固定 Kaikki/Wiktextract 快照构建，以 OEWN/COW 做英文义项或一致性辅助；本地索引覆盖尽可能多的可验证表达/义项。
- **路线 B：高频核心包＋本地模型兜底。** 只内置数千个经审计的高频表达/义项；其余的缺词、MWE、俚语或义项冲突在用户主动配置的 Ollama/LM Studio 上，用最小语境请求本地模型，并将可复用结果放入受版本约束的本地缓存。

本文只把数据维护方、模型/Provider 维护方的官方资料和原始研究作为事实来源。它不是法律意见，也不把任意模型输出称为词典事实。

## 结论先行

### 没有一份现成的“专用词典”恰好等于本产品所需能力

这个判断是成立的，但需要精确表述：**不是没有可用的词典数据，而是没有一个现成数据源同时解决以下六件事**：

1. 按英语表达、词性和义项组织；
2. 给出可靠、可在 `cat（猫）` 中展示的简中短释义；
3. 对当前网页句中的多义词和 MWE 完成正确消歧；
4. 离线、可随本地扩展使用；
5. 逐版本可追溯、可复现、可做许可证审计；
6. 能在用户反馈后变成“这个用户在这个义项是否需要提示”的个人化判断。

Kaikki/Wiktextract 有英语词形、词性、英文 gloss，以及**存在时**的各义项中文翻译候选；但它不保证每个义项都有可靠、简体且短的中文候选。OEWN 是英语义项网络，并不提供中文释义；COW 的公开数据主要是中文词元与 PWN 义项的映射，也不是当前句可直接显示的中文定义。三者边界的详细证据见本项目已有的[词典来源、许可与清洗复核](2026-07-17-dictionary-source-licensing-and-cleaning-research.md)。

因此，所谓“自己的词典”不应理解为人工编写一本英汉词典；它应是**基于可审计上游、针对阅读场景清洗出的本地词汇知识包**。本产品的“当前义项”和“用户是否会”仍必须由表达识别、语境判断和用户证据分别处理，任何一本公共词典都不能替代它们。

### 两条路线不是非此即彼；推荐把 B 作为可控的 V0.1 范围，把 A 的构建能力保留为长期基础设施

`RULES.md` 已确认“本地词典是正常阅读和常规查询的核心能力；本地模型不是必要依赖，且可靠词典命中不得调用模型”。所以“完全无内置词典、全部交给 LLM”不在当前已确认边界内，也不应作为这次二选一的候选。

研究建议是一个有明确边界的组合：

1. **先做小而可审计的高频核心包。** 它依旧采用 Kaikki/Wiktextract 的固定快照与清洗门禁，只是首版不承诺把长尾全部打进扩展。它覆盖正常、高频、低歧义命中，提供即时且离线的短释义。
2. **模型只处理明确的洞：** 核心包缺词、MWE/俚语、词典义项冲突，或用户主动要求“结合上下文解释”。模型结果标为“本地模型解释”，不能取代词典来源或用户直接反馈。
3. **缓存是可淘汰的解释缓存，不是未经验证的新词典。** 缓存能避免相同表达—义项—版本组合重复调用，但不得仅按 `word` 复用，也不得跨义项或跨模型/Prompt 版本静默当作稳定事实。
4. **当 PoC 显示模型兜底频率太高、释义错误不可接受或设备体验不稳定时，再扩大 A 的覆盖。** 反之，不为尚未验证的长尾覆盖先投入一次性大规模清洗。

这不是宣称 B 的释义质量会“自动达到 95%”。两个 95% 产品指标分别是未知表达识别与用户经复测确认掌握，均不能由词典/模型单项准确率替代。

## 一、可核查事实与边界

### 1. 上游词典数据能提供什么，不能提供什么

- Kaikki 的原始 Wiktextract 数据以 JSONL 发布，英语条目可有 `word`、`pos`、`forms`、`senses`、英文 gloss 与翻译；翻译既可能是义项级 `senses[].translations`，也可能是未消歧的条目级候选。Wiktextract 官方字段说明还指出翻译中的 `sense` 是自由文本，不能假定与 gloss 一一对应。[Kaikki 原始数据说明](https://kaikki.org/dictionary/rawdata.html)、[Wiktextract 格式与翻译字段](https://github.com/tatuylonen/wiktextract#format-of-the-extracted-word-entries)。
- OEWN 是按 synset 组织的英语 lexical network，发布英语词元、定义和语义关系；它没有把中文短释义作为数据字段发布。[OEWN 官方仓库](https://github.com/globalwordnet/english-wordnet)。
- COW 经 OMW 发布的 `cmn` 数据是与 PWN 3.0 义项相连的中文 lexical unit；这可以成为一致性信号，却不是一个已消歧的英→简中短释义库。[COW/OMW 格式说明](https://omwn.org/omw1.html)、[COW 原始许可证](https://github.com/bond-lab/cow/blob/master/docs/LICENSE)。
- 可再分发的数据包不能只看抽取器许可证：Wiktextract 工具是 MIT，而 Wiktionary 原始条目还涉及 CC BY-SA 4.0/GFDL；OEWN 的 CC BY 4.0 发布还要求 OEWN 和 Princeton WordNet 署名；COW 有自己的 notice/免责声明保留要求。[Wiktionary 版权页](https://en.wiktionary.org/wiki/Wiktionary:Copyrights)、[OEWN LICENSE](https://github.com/globalwordnet/english-wordnet/blob/main/LICENSE.md)。

**事实推论：** A 不能绕过清洗与许可审计；B 也不能绕过，因为 B 的高频包仍是一个需再分发的词典包。差别只在首版把哪部分覆盖放进本地静态包。

### 2. 本地 Provider 能提供什么，不能保证什么

- Ollama 安装后的默认 API 是 `http://localhost:11434/api`，支持 JSON Schema 结构化输出；官方建议低温度并由调用方进行 schema 校验。[Ollama API](https://docs.ollama.com/api/introduction)、[Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)。JSON 合法只证明接口形状，不证明中文释义或义项正确。
- Ollama 响应提供加载、输入处理、生成时长及 token 计数，适合把冷/热启动、生成吞吐和端到端时延记入本机 PoC；不应以网上 benchmark 外推本机性能。[Ollama Usage](https://docs.ollama.com/api/usage)。
- LM Studio 在模型/运行时已在本机时可离线运行，本地 server 的请求可留在本机；但它也可以被配置为对局域网开放。其 CLI 的默认 bind 为 `127.0.0.1`，非 loopback 绑定会暴露服务，因此扩展必须实际校验目标地址，而不能只依赖“用户说自己在本地”。[LM Studio 离线运行](https://lmstudio.ai/docs/app/offline)、[LM Studio server bind](https://lmstudio.ai/docs/cli/serve/server-start)。
- LM Studio 和 Ollama 均可基于 JSON Schema 生成结构化输出；LM Studio 明确警告，尤其是小于 7B 的模型未必可靠地支持结构化输出。[LM Studio Structured Output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)。

**事实推论：** Provider 让 B 在隐私边界内技术上可行，但它们不带“释义准确性保证”。请求仍应只发目标表达、所在句和规则允许时的相邻句，且只允许 loopback；这与既有 `RULES.md` 保持一致。

### 3. Qwen 的模型事实与不能下的结论

Qwen 官方模型卡将 `Qwen3-1.7B` 标为 1.7B 参数、Apache-2.0、32,768 context；Qwen3 系列声明支持 100 多种语言/方言，并列出 Ollama、LM Studio 等本地使用方式。`Qwen3-8B` 同为 Apache-2.0 模型，原始仓库文件约 16.4 GB；这不是量化后本机内存占用的承诺。[Qwen3-1.7B 官方模型卡](https://huggingface.co/Qwen/Qwen3-1.7B)、[Qwen3-8B 官方模型卡](https://huggingface.co/Qwen/Qwen3-8B)。

Qwen 官方说明中，non-thinking mode 用于提高效率；这适合“单表达＋一两句语境→短释义”的候选实验模式，但不是“更准确”的证据。[Qwen3 模式说明](https://huggingface.co/Qwen/Qwen3-1.7B#switching-between-thinking-and-non-thinking-mode)。

**不能从官方资料得出的结论：** 没有官方资料在“英文网页中的多义词/MWE → 简中短释义”这一任务、统一量化和统一 CPU/GPU 环境下，比较 1.7B 与 8B 的正确率、P95 时延或内存；因而不能把任何一个写成“最快最准的默认模型”。量化类型、上下文长度、CPU/GPU/统一内存、offload、Provider/runtime 版本都会改变结果。

## 二、路线 A 与路线 B 的产品/工程对比

| 维度 | A：广覆盖可审计核心词典 | B：高频核心包＋本地模型兜底 | 结论 |
| --- | --- | --- | --- |
| 正常阅读离线性 | 包命中时完全离线、即时；长尾是否可用取决于包覆盖 | 高频包命中完全离线；长尾仅在用户已装、已启用、正在运行模型时可解释 | B 不得让模型成为必需依赖；缺模型时须明确降级而非阻塞 |
| 首次时延 | 本地索引/查表，不需要模型加载 | 缓存未命中的兜底需要模型加载、提示处理和生成；冷启动可能明显慢于查表 | B 必须把模型请求从普通可靠命中路径移走，且能取消/超时 |
| 隐私 | 静态包不发送网页文本 | 语境只进 loopback，仍多了一条本地服务边界；Provider 可被用户错误配置为 LAN | 两者都可符合 V0.1；B 需严格地址白名单和数据最小化 |
| 许可/供应链 | 需持续审计 Kaikki/Wiktionary、OEWN、COW 及自己的构建物 | 高频包仍承担同一词典许可义务；另需记录模型、量化物、runtime/Provider 的许可证和版本 | B 降低首版覆盖，不降低许可责任 |
| 可审计性 | 每条可保留 source sense、源快照、清洗规则、哈希；错误可重跑追溯 | 模型答案受模型、量化、Prompt、语境影响，必须记录生成合同；不能仅凭 `confidence` 自报判断正确 | A 更适合作为“词典事实”；B 的输出只能是候选解释 |
| 冷启动覆盖 | 有机会一次覆盖更广，前提是先完成清洗、体积和质量验证 | 几千高频项快速支持大多数常规阅读，但长尾第一遇会有失败、等待或需要手动请求 | B 更快验证闭环；“几千”不能在未做目标语料覆盖前宣称足够 |
| 长期维护 | 快照更新、sense 映射、迁移、许可证和回归 fixture 工作量大 | 除核心包工作外，还有 Provider 协议、模型/Prompt 漂移、缓存失效和硬件差异 | B 不是零维护，减少的是首版数据面，不是复杂度总和 |
| MWE/当前义项 | 可以把已收录 MWE 作为独立表达；未收录 MWE/歧义仍需要候选识别和拒答 | 模型可使用句境解释长尾 MWE，但可能忽略边界、虚构或错误消歧 | MWE detection 是独立问题；两条路线都不能只按 lemma 缓存或传播状态 |
| 用户反馈闭环 | 可将“释义不对/不会/会了”与可追溯 sense 区分 | 可以把用户纠正作为最高优先级证据，但不得让一次模型解释反过来覆盖它 | 用户直接证据优先级在两条路线中相同 |

## 三、推荐的受控组合与失败降级

### 建议的三层职责

```text
固定快照的高频核心包（词典事实、即时）
        ↓ 缺词 / MWE / 义项冲突 / 用户主动请求
最小语境的本地模型（“本地模型解释”、可拒答）
        ↓ 仅在同一表达—义项—版本合同内命中
可淘汰本地解释缓存（加速，不成为用户掌握事实）
```

这是建议，不改写当前规则。具体而言：

1. 当前网页提示记录只保留 `expression`、简化 `pos` 和 `short_zh`。`sourceSenseId/fallback`、英文 gloss、中文候选、来源快照、许可引用、清洗规则和质量状态属于独立构建审计外壳，不得混入用户提示载荷。核心包不是手工词表，也不是“模型曾经说过的答案”集合。
2. 兜底模型的可显示输出也只落到 `expression / pos / short_zh` 或明确拒答；表达边界、候选粗义项／英文 gloss、解释来源类型和生成版本保留在独立审计记录。模型不应决定用户是否会、不应扫描整页、也不应把输出伪装为字典释义。
3. 对模型返回的 `confidence`，只可把它当作模型附带信号；展示强度仍应由外部校准/人工审计决定。格式校验、低温度和 JSON schema 不能修复语义错误。
4. 词典可靠命中、模型异常、模型未配置、超时或目标页面已变化时，都必须回到已有规则中的英文 gloss／轻提示／“需要更多上下文”；绝不阻塞阅读或编造释义。

### “高频”如何确定

不能从一份通用频率表直接推出本用户的高频阅读表达，也不能只数单词后把 MWE 漏掉。首个核心包应从目标文本而不是考试词表反向选取：新闻、博客、Wikipedia、技术文档各保留固定语料，按**表达候选**统计覆盖；`run into`、`set up`、多义词、屈折和技术术语要单列。然后报告：

- `lemma hit`、`expression/MWE hit`、`sense hit`、`可靠简中短释义 hit`；
- 因缺词、义项冲突、低质量中文候选而转入模型/轻提示的比例；
- 核心包体积、许可证清单和每次构建的变更。

只有该覆盖报告才能回答“数千项够不够”。在此之前，数千是一个成本控制范围，不是已证实的最佳规模。

## 四、模型缓存：能避免重复调用，但必须按“解释合同”失效

用户提出“高频的记录到本地词库不重复调用”是可行的，但正确的实现不是 `word → 中文` 的永久 Map。`bank`、`address`、`run into`、派生词和同形异义会使这种 Map 立刻污染后续页面。

### 建议缓存层级

| 层 | 保存什么 | 能否跨页面重用 | 淘汰/失效 |
| --- | --- | --- | --- |
| 静态词典 | 清洗过的表达—义项—短释义及上游追溯 | 可以，但仅限同一已确认义项 | 随词典包版本迁移；可回滚 |
| 用户直接证据 | “会/不会”、直接复测、必要证据摘要 | 仅在同一表达—粗义项高置信成立时 | 受保护，不被缓存整理/模型覆盖 |
| 模型解释缓存 | 受限语境下的候选释义、拒答、模型/Prompt/词典版本和生成时间 | 仅当表达边界、词性/粗义项和版本合同都匹配，且没有更高优先级来源 | 可淘汰；模型、Prompt、词典、语境策略或解析器变化即失效或降为待复核 |

建议的缓存键至少包括：

```text
规范化表达 + 表达边界/MWE 标识 + 词性（若可得） + 粗义项候选/解析器版本
+ 词典包版本 + Provider 协议版本 + 模型精确标识/量化 + Prompt/JSON-schema 版本
+ 语境截取策略版本 + 目标语言
```

这不是要求长期保存 URL、标题或浏览历史。若缓存需要保存最小语境来判断能否复用，它应受现有的容量、代表语境和隐私规则约束；未获用户反馈的模型缓存属于可淘汰数据，不能成为个人知识状态。冲突合并仍按已确认优先级：用户直接反馈/同义项直接复测 > 当前义项正确且来源可靠的词典内容 > 其他可淘汰解释缓存；短文本只能在正确性和可靠性等价后胜出。

## 五、早期 PoC 样本量建议（已被当前分阶段执行口径取代）

### 目的与样本

本研究最初建议一次做 **180 或 240 条**，用于说明人工金标的构成与统计局限；该建议不再是当前执行顺序。当前第一阶段总计 500 条，先用其中 100 条验证 Harness 与输出合同，只有通过 Codex Gate 才按 100 条里程碑继续到 500；整批不证明正式覆盖规模，未经新门禁不扩到 1000。样本均应只保留复现实验所需的句子及目标表达，按现有最小语境边界保存，不下载整站或整篇文章，并至少分层覆盖：

- 新闻、博客、Wikipedia、技术文档；
- 高频单义、屈折/透明派生、多义词、MWE/俚语、低频/术语；
- 可由词典可靠命中的项、词典缺中文的项、候选冲突的项。

每条金标包括表达边界、词性（可为未知）、目标粗义项、可接受简中短释义集合、不可接受的常见错误、是否允许英文 gloss/拒答。先由两位审阅者独立标注，再记录并裁决分歧；若只能由一人完成，则如实把它写成单人 dogfood 金标，不能伪装为客观全人群结论。

### 对照条件与指标

| 条件 | 输入/行为 | 主要测量 |
| --- | --- | --- |
| A | 清洗后的 Kaikki 核心数据（OEWN/COW 仅辅助） | 覆盖、正确当前义项、可靠简中短释义、错误强提示、MWE 漏项 |
| B1 | 数千高频核心包；不调用模型 | 高频核心覆盖是否足以支撑普通阅读、会有多少项走轻提示/缺词 |
| B2 | B1 的缺词/冲突走真实本机模型；第一次为冷缓存 | 模型语义正确、可接受短释义、明确拒答正确、JSON 无效/超时、冷启动和 P95 时延 |
| B3 | 与 B2 相同输入再跑一次；命中受版本约束缓存 | 缓存命中、复用正确率、热路径时延、错误跨义项复用率（必须为零容忍的回归项） |

所有条件使用同一表达识别器、同一用户反馈规则与相同最小语境，不能一边改变模型又一边改变提示密度。报告不只给平均正确率，还必须分别给：当前义项正确率、短释义可接受率、MWE 边界正确率、错误强提示率、拒答正确率、词典/模型/缓存命中比例、P50/P95 冷热端到端时延、结构化输出有效率以及失败降级是否保持可读。

### 模型候选和真实本机验证

第一轮只把严格小于 4B、且已有已确认 Provider 路径的 `Qwen3-1.7B` 放入产品可行性基准。是否加入第二个严格小于 4B 的候选，须在第一轮结果后另行确认；`Qwen3-8B` 不属于当前小于 4B 的候选范围。对每个实际纳入的候选锁定：官方仓库 revision、模型文件/量化哈希、Provider/runtime 版本、上下文长度、是否 non-thinking、采样参数和 Prompt/Schema 版本。

每个实际纳入的模型分别经真实的 Ollama 与 LM Studio（两者中用户实际会使用的 Provider 至少一个）运行并记录：

1. 首次加载到可请求的时间、冷请求 P50/P95、热请求 P50/P95；
2. prompt tokens、completion tokens、Provider 给出的加载/输入/生成时长；
3. RAM/VRAM、CPU/GPU offload、失败/取消/超时和无效 JSON；
4. 上表的语义和短释义金标指标。

这份实测先回答“Qwen3-1.7B 在此用户机器上是否够快、够稳、够安全”；只有另一个严格小于 4B 的候选获得确认后，才比较“哪一个更合适”。不下载未授权模型、不把模型作为默认安装前，不能用网络 benchmark 替代本机证据。Qwen 的 non-thinking mode 可以作为速度条件，但必须与同模型 thinking 条件分开记录，不能先假定更快就一定足够准确。

## 六、阈值与参数：研究能给原则，不能代替 PoC/dogfood

### 有可迁移研究支持的原则

1. **样本量按精度预注册，不按“1000 个看起来很多”决定。** NIST 对比例估计给出样本量与容许误差、置信水平及预期比例的关系；pilot 研究的方法论文也主张以置信区间精度而非显著性为主。[NIST 比例样本量说明](https://www.itl.nist.gov/div898/handbook/ppc/section3/ppc333.htm)、[O'Neill, 2022](https://doi.org/10.1371/journal.pone.0262804)。作为量级提示，若观察到 90% 通过，100 条的 95% Wilson 区间约为 **82.6%–94.5%**，300 条约为 **86.0%–93.0%**；因此 100–300 足以比较路线、暴露失败类型，却不足以证明对所有英语网页的 95% 性能。应按关键分层分别报告分母和区间。
2. **响应时间以分布和用户任务衡量，而不是单一平均值。** 经典人机交互研究把约 0.1 秒、1 秒、10 秒分别视为“即时感”“不中断思路”“注意力仍可能维持”的不同量级；该研究早于今天的浏览器与本地模型，不能直接成为硬 SLA，但支持分别记录冷/热 P50/P95、取消率和阅读打断，而不是只报平均延迟。[Miller, 1968 原始论文](https://doi.org/10.1145/1476589.1476628)。
3. **释义可读性必须用任务验证，而不是从汉字数推出。** L2 词汇注释研究显示 gloss 形式/语言、文本难度和学习者会影响阅读与学习结果，且既有研究并不支持一个跨设备、跨文本的“最佳中文长度”。[Abraham, 2008 的 gloss 元分析](https://doi.org/10.1080/09588220802090246)、[Cheng & Good, 2009 原始研究](https://eric.ed.gov/?id=EJ859583)。所以人工金标应额外判定“当前句可用且不误导”“一眼可读/需悬停”“过长/含多义污染”，并和行内布局 dogfood 一起看。
4. **缓存失效以输入语义与生成合同为边界，而不是时间 TTL 单独决定。** 这是软件正确性原则而非某篇论文能给出的一个秒数：当模型、量化、Prompt/Schema、词典、表达解析器或最小语境策略变化时，旧输出不能仍被视为同一结果；用户反馈优先级不能被缓存覆盖。TTL 只能在这些必需键之后作为容量/陈旧性工具。

### 必须由 PoC 和连续两周 dogfood 冻结的参数

- 高频核心包究竟是 3 千、5 千、1 万还是别的规模，及其按网页语料的 coverage 门槛；
- 简中短释义的最大长度、是否允许多个候选、何时降级为英文 gloss；
- 词典可靠度、模型输出可靠度、强提示/轻提示/拒答的概率或规则阈值；
- 1.7B 与任何后续获确认的严格小于 4B 候选（以及具体量化）在本机的冷/热 P95、超时、串行队列和并发/取消配置；
- MWE 识别、义项解析、缓存复用的精确接受条件；
- `RULES.md` 中仍待确认的抽检间隔、审计样本构成、性能门槛、模型缓存失效细节和 dogfood 退出条件。

以上参数会随用户机器、网页排版、文本类型、初始词汇水平、模型版本和Provider变化。研究不能诚实地给出一个普适“最佳数”；正确做法是写入 PoC 预注册表：候选值、比较指标、最小可接受边界、失败时回退策略和冻结日期。两周 dogfood 的作用是为这个单用户产品选择可撤销的安全默认值，而不是宣称发现总体人群最优。

## 七、进入下一阶段前的可判定决策

本研究建议在可丢弃 `/prototype` 中先回答以下问题，再重新执行 `/to-spec`：

1. 目标语料上，高频包的 `可靠简中短释义 hit` 是否足以让模型只成为少量兜底，而不是正常阅读主路径？
2. 同一金标集上，模型 B2 是否显著减少“词典暂缺/轻提示”，且没有把错误强提示或 MWE/义项错配带到不可接受程度？
3. B3 是否能做到只在正确的表达—义项—版本合同下复用；缓存失效、撤销、页面离开和模型失败是否全都安全降级？
4. 在用户实际 CPU/GPU 上，模型冷/热延迟和内存是否能在不阻塞阅读的情况下工作？
5. 高频包、模型以及生成缓存的来源/许可证/版本/删除边界是否能被数据与隐私页如实说明？

如果第 1、3、4 任一项失败，不能以“LLM 之后会更好”跳过 A 的数据质量门禁；应扩大/修正核心包或把模型限定为手动解释。若它们通过，首版可以从小核心包＋受限兜底开始，把广覆盖 A 作为可审计的逐步扩展，而不是阻塞用户反馈闭环的前置大工程。
