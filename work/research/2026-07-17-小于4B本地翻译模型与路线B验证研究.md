# 小于 4B 本地翻译模型与路线 B 验证研究

**日期：** 2026-07-17
**状态：** 只读研究笔记；不冻结模型、技术栈、Provider 协议或质量阈值。本文的 180／240 条是早期研究建议；后续已确认执行口径为“先冻结 Codex→Hermes→Reasonix Harness → 第一阶段总计 500 条，前 100 条为其中的合同门 → 每 100 条反思并沉淀候选 Skill”，以 `RULES.md` 为准。
**问题：** 路线 B 需要一个严格小于 4B 参数、适合英→简中的本地模型。能否优先选择翻译专用模型，并保持已确认的 Ollama / LM Studio Provider 边界？
**资料范围：** 只采用模型发布者、维护方模型卡、官方运行时文档和原始论文；没有下载模型或数据。

## 结论先行

截至本次核查，**没有一个候选同时被一手资料证实满足以下四个条件**：

1. 严格少于 4B 参数；
2. 专门为机器翻译训练，并覆盖英语→简体中文；
3. 可用于本项目的“目标表达＋最小语境→极短中文释义”，而不只是整句翻译；
4. 可直接由项目已确认的 Ollama 或 LM Studio Provider 路径运行。

因此，路线 B 的正确验证方式不是把未证实可运行的翻译模型塞进产品，而是分成两个不混淆的问题：

```text
产品可行性 PoC（本轮推荐）
  Qwen3-1.7B，经 Ollama / LM Studio
  → 验证最小语境、短释义、结构化结果、缓存与失败降级

翻译模型质量参照（不进入产品 Provider）
  OPUS-MT en→zh：小体积、Apache-2.0、目标包含 cmn_Hans
  MADLAD-400-3B-MT：较大规模的 Apache-2.0 参照
  → 仅在官方 Transformers 等路径下比较“整句翻译”能力；不可替代产品 PoC
```

`Qwen3-1.7B` 是**通用指令模型对照**，并非翻译专用模型；它之所以是本轮路线 B 的主候选，是因为它严格小于 4B、官方声明支持多语言指令和翻译，且 Ollama 与 LM Studio 都给出可使用的本地模型路径。它不能被宣传为“翻译模型最好”或“已达到本项目准确率”。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-1.7B)、[Ollama Qwen3](https://ollama.com/library/qwen3)、[LM Studio Qwen3-1.7B](https://lmstudio.ai/models/qwen/qwen3-1.7b)

这也不改变已确认的产品规则：可靠核心词典命中仍不得调用模型；模型只处理缺词、MWE／俚语、义项冲突或用户主动要求的上下文解释；结果只能标为“本地模型解释”。

### 1. MADLAD-400-3B-MT：最接近“<4B 翻译专用”的质量候选，但不在当前 Provider 合同内

Google 的原始仓库把它列为 “3B parameter MT model”；模型卡称其为基于 T5 的机器翻译模型，支持 400+ 语言，并说明用目标语言 token `<2xx>` 控制翻译。原论文的语言表含 Mandarin Chinese（`zh`）。模型卡的原始浮点文件大小为约 11.8 GB；同页给出了 Candle 运行时的 1.65 GB Q4 示例，但这不是 Ollama/LM Studio 的官方发行物，也不是本项目可以直接承诺的下载量。[Google 原始仓库](https://github.com/google-research/google-research/tree/master/madlad_400)、[Google 模型卡](https://huggingface.co/google/madlad400-3b-mt)、[MADLAD-400 原论文](https://arxiv.org/abs/2309.04662)

它的模型接口是“翻译文本”，例如 `<2pt> I love pizza!`，不是聊天或 JSON 指令接口。因而即使它把整个英文句子译对，也**不自动等于**能可靠给出某一目标表达的短释义；从全句译文中抽取词组义项又会另建一个未验证的算法。

Ollama 官方文档对 Safetensors 导入列出的架构是 Llama、Mistral、Gemma 和 Phi3，并未列 T5；LM Studio 官方文档只承诺可导入“兼容的 GGUF”，没有在其资料中确认 MADLAD/T5 兼容。因此不能把社区 GGUF、论坛经验或“文件扩展名是 GGUF”当作项目 Provider 可用的证据。[Ollama Modelfile](https://docs.ollama.com/modelfile)、[LM Studio 导入模型](https://lmstudio.ai/docs/app/advanced/import-model)

**可保留的作用：** 若后来得到“允许为翻译模型新增本地 adapter / local service”的独立产品与架构决定，它可作为最有价值的 <4B 翻译质量对照；当前不应据此扩展 Provider 范围。

### 2. OPUS-MT en→zh：最小、许可更干净的翻译对照，但仍不是产品模型

Helsinki-NLP 发布的 `opus-mt-en-zh` 是英语→中文的 Marian 翻译模型；模型卡规定以 `>>cmn_Hans<<` 指定简体中文目标，发布树中的原始 `pytorch_model.bin` 约为 312 MB，许可证为 Apache-2.0。与 MADLAD 相比，它更适合作为“低下载量、英→明确简中”的**翻译质量基准**。[OPUS-MT 模型卡](https://huggingface.co/Helsinki-NLP/opus-mt-en-zh)、[OPUS-MT 发布文件](https://huggingface.co/Helsinki-NLP/opus-mt-en-zh/tree/main)

但发布方资料没有给出精确参数量，也没有给出 Ollama 或 LM Studio 的官方可运行交付；因而不能把 312 MB 文件大小偷换为“官方已确认严格 <4B 参数”，更不能把一个社区 GGUF 当成已确认 Provider。它仍只做整句翻译，不能直接回答“某目标表达在给定语境中是什么意思”。

### 3. NLLB-200 distilled-600M：覆盖明确，却被许可、用途与 Provider 三重排除

Meta 的模型卡明确写明该 checkpoint 为 600M distilled 版本、覆盖 196 种语言，语言表含简体中文 `zho_Hans`；官方 Transformers 文档定义通过 `src_lang` 和 `forced_bos_token_id` 选择源/目标语言。其发布包当前列为 2.48 GB（权重约 2.46 GB）。[Meta 模型卡](https://huggingface.co/facebook/nllb-200-distilled-600M)、[NLLB 官方 Transformers 文档](https://huggingface.co/docs/transformers/en/model_doc/nllb)

但同一模型卡给出 CC-BY-NC-4.0，明确主用途是机器翻译研究，并明确“不发布用于 production deployment”。本项目虽先是个人 dogfood，仍要为未来产品路线保留清晰的再分发与生产边界，因此不应让它成为 V0.1 的默认模型；而且没有官方资料证明其 M2M100 架构可直接由项目要求的 Ollama/LM Studio 路径运行。

另一个专用翻译 checkpoint `facebook/m2m100_418M` 是 418M、MIT；其官方接口同样依靠源语言与强制目标语言 token，但当前可核查资料只写 `zh`，没有将简体中文单列，也没有给出所需 Provider 的端到端运行路径，所以不取代 OPUS-MT 或 Qwen 作为本轮重点。[M2M100 模型卡](https://huggingface.co/facebook/m2m100_418M)、[M2M100 官方 Transformers 文档](https://huggingface.co/docs/transformers/en/model_doc/m2m_100)

### 4. TranslateGemma：重要反例，而不是可悄悄放宽的入选者

Google的 TranslateGemma 是最接近所求产品形态的模型：模型卡明确称其为翻译模型，输入为待翻译文本、输出为目标语言文本；Ollama 官方库给出 chat API 与 `translategemma:4b` 的约 3.3 GB Q4 下载物。[Google 模型卡](https://huggingface.co/google/translategemma-4b-it)、[Ollama TranslateGemma](https://ollama.com/library/translategemma)

它仍不合格：用户要求是**参数量**严格小于 4B，不是“Q4 文件小于 4 GB”。其命名为 4B，模型卡页面还列为 5B 参数，任一口径都不能证明严格小于 4B。若未来用户明确放宽到“4B 级”，才应把它加入新的对照实验，并独立审核 Gemma 使用条款。

### 5. Qwen3-1.7B：本轮可验证产品路径的主候选，而非翻译专用替身

Qwen 官方模型卡给出 1.7B 参数、Apache-2.0、32,768 token 上下文，并把“多语言指令遵循和翻译”列为系列能力。Ollama 官方库明确提供 `qwen3:1.7b`，当前页面列为约 1.4 GB；LM Studio 官方模型页列出该 1.7B 模型的 GGUF 与 MLX 具体来源，并标示最低系统内存 1 GB。这些是本地下载物和应用的陈述，不是实际运行所需峰值内存或本项目的时延保证。[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3-1.7B)、[Ollama Qwen3 标签](https://ollama.com/library/qwen3)、[LM Studio Qwen3-1.7B](https://lmstudio.ai/models/qwen/qwen3-1.7b)

它的关键优势不是“翻译专用”，而是可以接受**目标表达、完整所在句、必要时相邻句、候选英文 gloss 和严格输出指令**，从而直接回答本项目真正的问题。这个能力必须实测，不能由通用模型卡外推。

## 二、为什么不能把“整句翻译正确”当作路线 B 通过

产品需要回答的是：

```text
目标表达：run into
最小语境：The team ran into a licensing problem.
需要输出：遇到
```

而不是：

```text
团队遇到了许可问题。
```

整句译文可能流畅，却仍可能出现下列产品级失败：

- 把 `run into` 误拆为 `run`，使 MWE 反馈和缓存键错误；
- 正确翻译句子却没有给出可放入 `cat（猫）` 的短释义；
- `address` 在句中是“处理”，模型却输出常见义“地址”；
- 输出解释、整句、多个义项或无效 JSON，破坏行内显示；
- 不确定时仍编造短释义，而不是拒答／降级。

翻译专用模型的官方任务格式也印证了这个差异：MADLAD 以目标语言 token 加待翻译文本驱动；NLLB 的官方接口设定源语言和目标语言 token；它们都没有把“指定表达边界、按当前义项生成极短 gloss、返回可验证结构”作为已证明能力。[MADLAD 使用说明](https://huggingface.co/google/madlad400-3b-mt)、[NLLB 使用说明](https://huggingface.co/docs/transformers/en/model_doc/nllb)

## 三、路线 B 的可丢弃实测协议

### 1. 先验证的假设

> 在不调用模型处理可靠词典命中的前提下，`Qwen3-1.7B` 经已确认的 loopback Ollama 或 LM Studio，可对核心包的缺词／义项冲突／MWE 返回可验证的中文短释义；失败时能无阻塞降级，且缓存不会跨义项污染。

这只验证路线 B 的产品可行性，不验证“Qwen3-1.7B 是最优翻译模型”，也不把模型输出提升为词典事实。

### 2. 固定输入与结构化输出

每一条请求最多包含既有隐私规则允许的字段：

```json
{
  "expression": "run into",
  "sentence": "The team ran into a licensing problem.",
  "neighbor_sentence": null,
  "candidate_english_glosses": ["encounter a difficulty"],
  "task": "仅解释 expression 在 sentence 中的意思；不要翻译整句。"
}
```

PoC 输出可以暂定为可校验的实验 schema：

```json
{
  "status": "ok | insufficient_context | reject",
  "expression": "run into",
  "short_zh": "遇到 | null",
  "sense_en": "encounter a difficulty | null"
}
```

`short_zh` 为空并不自动失败：在语境不足、表达边界不成立或模型不确定时，`insufficient_context` / `reject` 是正确的安全行为。PoC 必须在调用方验证 JSON、`expression` 回显、长度、禁止整句标点模式和与目标表达的匹配；模型的自报置信度不是正确性证明。

### 3. 金标、条件与计分

本研究最初建议同一批 180 或 240 条人工标注句子；该单批设计已被当前“第一阶段总计 500 条、前 100 条为其中合同门、此后按 100 条里程碑继续”的口径取代。整批都不下载整页、不保留 URL，并按下列类型分层：高频单义、屈折／透明派生、多义词、MWE／俚语、术语／低频词；新闻、博客、Wikipedia、技术文档均须有覆盖。每条金标包括表达边界、目标粗义项、可接受简中短释义集合、不可接受的常见误义和允许拒答条件。

对每一条运行四个条件，除模型／缓存外保持表达识别、最小语境与用户规则相同：

| 条件 | 目的 | 不可被替代的结果 |
| --- | --- | --- |
| B0：核心包 | 测真实核心词典覆盖 | 可靠简中短释义命中、冲突／缺词转交比例 |
| B1：Qwen3-1.7B 冷缓存 | 测首次模型兜底 | **目标表达义项正确率**、短释义可接受率、MWE 边界错误、拒答正确率、JSON 有效率、P50/P95 时延 |
| B2：同合同缓存命中 | 测重复调用是否真正可省 | 缓存命中率、热路径时延、复用后短释义仍与金标一致 |
| B3：故意改变义项／版本 | 测缓存隔离 | 跨义项复用必须为零；模型、Prompt、词典、解析器或语境策略变化后必须失效／降级 |

计分时，整句翻译质量只能作为诊断附注，不能计入“短释义通过”。一个 `address` 全句译得通顺、但返回“地址”，或 `run into` 被拆开，均属于产品失败。

### 4. Provider 与失败路径必须实测

在真正下载前，把下列内容预注册到原型记录：Ollama/LM Studio 版本、模型精确 tag/文件哈希、量化、上下文长度、是否关闭 thinking、temperature、Prompt/JSON schema 版本、超时与取消策略。每条请求只发 loopback，后台串行、去重、可取消；页面离开后丢弃结果。

必须分别模拟／实测：未启动、模型不存在、加载慢、超时、取消、无效 JSON、空输出、拒答与页面目标失效。每一种都必须回到核心词典、英文 gloss、轻提示或“需要更多上下文”，且不得阻塞阅读。Ollama 的 JSON Schema 结构化输出和 LM Studio 的结构化输出均可协助验证接口形状，但 LM Studio 官方明确提醒小于 7B 的模型可能不可靠地遵循结构化输出；因此 schema 有效只是必要条件，不是释义正确的证据。[Ollama Structured Outputs](https://docs.ollama.com/capabilities/structured-outputs)、[LM Studio Structured Output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)
