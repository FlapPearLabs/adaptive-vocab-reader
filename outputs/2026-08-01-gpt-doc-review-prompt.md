# 网页版 GPT：V0.1 文档与 Spec 审查提示词（防跑偏 + 防过度工程化）

## 用法

- **方式 A（推荐）**：先把文档推送到 `review/<主题>` 分支（或直接开 PR），把 `<COMPARE_URL>` 替换为 GitHub Compare 链接后发给网页版 GPT。
- **方式 B**：不推送，把 RULES.md、CONTEXT.md、规格、tickets 全文粘贴到提示词中标明的「粘贴位置」后发送。

---

## 提示词正文（复制以下全部内容）

```text
请作为严格的产品与软件审查员，审查我的浏览器词汇学习插件 V0.1 的 Grill 产物：项目规则文档、领域术语表、施工规格与本地 ticket。重点检查两件事：是否「跑偏」（范围越界、偏离用户真实需求），是否「过度工程化」（复杂度超过当前闭环所需）。

【输入】
- 方式 A：公开 GitHub 链接 <COMPARE_URL>。审查该链接涉及的全部变更文件，重点是 RULES.md、CONTEXT.md、docs/specs/2026-07-30-V0.1-重新对齐规格.md、work/tickets/2026-07-31-v0.1-realign/ 六个 ticket。
- 方式 B：直接粘贴文档全文（粘贴位置：<在此粘贴>）。

【审查基准（按优先级）】
1. RULES.md 中标记 [已确认] 的条目——唯一产品规则来源；[待确认] 条目不是已确认需求。
2. 用户 2026-07-30/31 Grill 阶段逐题确认的决定（规格 §3 决策追踪 GR-01~GR-11、CR-01~CR-06）。
3. CONTEXT.md——领域术语权威。
4. docs/specs/2026-07-30-V0.1-重新对齐规格.md——当前施工规格。
5. 旧规格（2026-07-22 三份）与旧 GitHub Issue 只作历史证据，冲突时一律让位，不得作为新增需求依据；不得根据旧 ticket、注释或提交信息臆造新需求。

产品用户闭环（V0.1 全部范围）：
阅读英文网页（wordKey 提示）→ 50 题首测（写状态+证据）→ 看到单点估计 + 保守范围 → 每天可选五题校准 → 手动 会/不会 改提示（不碰证据）→ 持久化 → 7 天/20 篇人工 dogfood → 用户明确接受或拒绝。

【检查一：是否跑偏（范围越界 / 偏离用户真实需求）】
1. 是否有文档或 ticket 把 [待确认] 条目、研究结论、建议或旧 Spec 写成了已确认事实？
2. 是否恢复了已被明确取代的旧范围：约 10,000 词门槛、PAV/Beta 后验、Pool B、高置信自动隐藏、复杂隐藏词审计、受控回填、Kaikki/模型/LLM 清洗路线、SRS/遗忘曲线/通知/调度器/自动 popup、遥测日志？
3. 是否出现用户没有要求过的新功能、新模块、新字段、新流程、新统计声称（如"90% 置信区间""总体覆盖率"）？
4. 每个 ticket 是否都能回答「用户现在多得到了什么」？是否有 ticket 为不存在或不确定的用户场景服务？
5. ticket 的范围是否超出其主责任 Requirement ID 在 Spec §20 中定义的行为？

【检查二：是否过度工程化（复杂度超过当前闭环所需）】
1. 抽象层级、协议强度、模块拆分和测试数量是否超过当前用户闭环所需？是否出现通用 repository/service/controller 层、事件总线、调度器、migration registry、测试历史系统、新审计 facade、新完整性哈希、mock-only seam？
2. AssessmentEvidence 是否每词只留最新一条、不做事件溯源？DailyTestState 是否只承载当前一天一轮五题、不建队列/提醒？Wilson 是否只用于显示、不驱动任何自动行为？schema 2→3 是否是一次纯迁移、不建通用框架、不提供 3→2 降级？
3. 是否在为冻结的审计代码补测试、扩建 audit、或加固哈希/防篡改协议（Spec §17、R-AUD-5 只允许为 V0.1 用户路径补最小回归）？
4. 测试策略是否与风险匹配：是否用纯函数调用冒充真浏览器 E2E（Spec §21 约束）？是否以"测试数量"而不是"真实验证"作为验收依据？
5. 是否把简单问题复杂化：例如为一次性迁移引入框架、为单点估计引入过度统计基建、为不存在的扩展场景预留设计？

【检查三：一致性与可执行性】
1. RULES.md、CONTEXT.md、Spec、tickets 之间的术语、路径、Requirement ID、引用是否一致？
2. 每个 ticket 是否含明确范围、非目标、验收标准、真实验证命令、失败行为和反过度设计检查？
3. 是否存在两个 ticket 重复/重叠的责任，或一个 ticket 内部塞了多个可独立验收的变更？

【约束】
不要改代码；不要输出泛泛建议；不要为了让文档"看起来完整"而建议增加用户没要的能力。

【输出格式（严格遵守）】
VERDICT: PASS 或 CHANGES_REQUESTED
BLOCKERS: 每项写 文件/节号、问题、违反的规则或需求、最小修复建议；没有则写 无
NON_BLOCKING: 可选建议；没有则写 无
CODEX_HANDOFF: 若 PASS，给出一段不引入新需求、可直接交给 Codex 的实施/验收摘要；若未通过写「等待修复后重审」。
```
