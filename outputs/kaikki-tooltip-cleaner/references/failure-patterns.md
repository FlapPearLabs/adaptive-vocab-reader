# Hermes 实验真实失败模式

## F01：把证据顺序误当来源守恒

- 表现：`appear` 的证据数组顺序与 `short_zh` 顺序不同，但片段完全相同。
- 根因：校验器比较有序列表，而来源守恒只要求片段完全一致。
- 处理：比较多重集合；不重跑模型。

## F02：词性映射未冻结

- 表现：021–030 整批输出 `verb`，而展示合同只接受 `v`。
- 根因：任务书没有明确 `noun→n`、`verb→v`。
- 处理：冻结映射，仅重跑受影响批次一次。

## F03：冗余 source_word 回显造成假错误

- 表现：模型把输入的“繁体 /简体”source_word 回显成简体片段。
- 根因：把冗余回显误当权威来源。
- 处理：权威证据缩减为 `source_record_index + translation_index + selected_zh`，由指针回查输入。

## F04：同一 expression+pos 输出多条记录

- 表现：`case`、`match`、`runner` 分别产生两条名词记录。
- 根因：三字段运行时没有 sense id，无法稳定区分相同表达和词性的记录。
- 处理：同一 `(expression,pos)` 最多一条，最多合并 3 个来源片段；对受影响任务定向返工。

## F05：窄义被误当通用网页提示

- 表现：`set up` 的来源只有“下套／诬陷”，首次却被接受。
- 根因：只检查来源存在，没有检查候选能否形成通用默认提示。
- 处理：旧合同下曾降级为 `needs_review`。现合同允许在没有合格来源核心义时生成“建立／设置”等词典式短义，但必须使用受控兜底外壳并标为未验证生成项。

## F06：唯一候选不利于学习者

- 表现：`hold on` 唯一候选为“且慢”，来源成立但语体过旧。
- 根因：缺少提示中文可读性检查。
- 处理：不得把“且慢”静默改写；可生成现代词典式短义并按受控兜底标记，不能可靠生成时仍降级 `needs_review`。

## F07：来源覆盖缺口不能成为无标记自由补译许可

- 表现：`hold`、`bank`、`right`、`state`、多个屈折形式和 MWE 没有可展示简中；`bear`、`draft`、`stem from` 截断或失效。
- 根因：上游 Kaikki 当前来源包的中文覆盖不足。
- 处理：不补抓、不替换来源。来源有效但缺少合格中文时，可按受控兜底生成最多 3 个词典式短义；必须 `model_generated / verified=false` 并进入 `generated.jsonl`。截断、失效或无法可靠生成仍 `needs_review`／`reject`。

## F08：成本 0 与成本 UNKNOWN 混淆

- 表现：Hermes usage 同时返回 `estimated_cost_usd=0.0`、`cost_status=unknown`、`cost_source=none`；旧归一化只读取数值 0，错误放行。
- 根因：成本校验没有检查状态和来源。
- 处理：原始 usage 的占位值 0 不是账单证据。用户已确认 MiniMax 为已付订阅后，Hermes 阶段项目边际成本可记为 `SUBSCRIPTION_INCLUDED / 0 元`，但仍保留原始 UNKNOWN、调用次数和 token；按量调用仍须有可核对成本。

## F09：合法 JSON 被 Markdown fence 包裹

- 表现：101–110 的 M2.5 输出内容完全合法，但外层带有 ` ```json ... ``` `。
- 根因：模型忽略了“只返回纯 JSON”的传输要求。
- 处理：Harness 仅允许机械剥离唯一外层 JSON fence，并记录 `MARKDOWN_JSON_FENCE` 偏差；存在其它前后文字或无法安全剥离的 Markdown 时仍失败，不为此浪费模型重跑。

## F10：把“最多 3 个片段”误当成尽量填满

- 表现：111–130 中出现 `contain=包含；含有；蕴含`、`increase=增加；增长；增大`、`hope=希望；盼望；指望` 等同一 sense 近义堆叠。
- 根因：Skill 只规定上限，没有规定最小充分原则；模型把候选覆盖率置于网页提示简洁性之前。
- 处理：默认只选 1 个最简洁、通用、学习者友好的片段；只有覆盖另一个明显不同且常用的粗义项时才增加第 2／3 个，不用近义词填配额。

## F11：来源成立但不适合当前简体中文提示

- 表现：`imagine` 唯一候选是 `想像`，逐字来源成立，但不符合当前用户预期的大陆简体通行写法。
- 根因：来源守恒只能证明“没有自造”，不能自动证明展示质量合格。
- 处理：降级 `needs_review`；不得把 `想像` 自行转换为来源中不存在的 `想象`。

## F12：非接受结论遗漏原因码

- 表现：111–130 的 Skill 优化重跑正确返回全部 20 个任务，但 `imagine` 与 `live` 的 `reason_codes` 为空，导致两个结论未通过结构校验。
- 根因：Skill 示例只展示 `SOURCE_SUPPORTED`，没有明确所有决策都必须给至少一个非空原因码。
- 处理：冻结非空要求并给出常用码示例；只定向重跑包含受影响任务的最小连续范围，不重跑已通过的其余结果。

## F13：原因码与来源事实不一致

- 表现：`poc-126 imagine` 的输入存在中文候选 `想像`，模型正确选择 `needs_review`，但错误标记为 `NO_DISPLAY_ZH`。
- 根因：只校验了原因码非空，没有校验原因码陈述的来源事实；模型把“候选不适合展示”误写成“没有候选”。
- 处理：旧合同下，有候选但不适合当前简体中文提示时使用 `UNFRIENDLY_ZH`，没有候选才用 `NO_DISPLAY_ZH`。现合同优先尝试受控模型兜底；只有无法可靠兜底时才保留上述非接受原因码。脚本仍校验原因码与实际记录类型一致。

## F14：同一 sense 的近义词再次堆叠

- 表现：131–180 中出现 `receive=收到；接到`、`remain=留下；剩下`、`encourage=鼓励；激励`；每组证据的非空 `sense` 完全相同。
- 根因：Skill 虽写了最小充分原则，但校验器只检查中文片段不同，没有检查它们是否来自同一个 sense。
- 处理：同一记录内，相同的非空规范化 `sense` 最多选择一个片段；普通脚本以 `DUPLICATE_SENSE_FRAGMENT` 拒绝此类结果。

## F15：来源存在但中文与词性或展示语体不自然

- 表现：`offer` 名词选择“提供”，而同一 proposal sense 已有更自然的“提议”；`form` 动词选择无法独立显示的“构”。
- 根因：模型把来源指针成立误当成展示质量成立，Skill 对词性自然度和独立可显示性排序不够明确。
- 处理：先判断候选与 sense、词性的自然匹配，再比较常用性和长度；存在更自然的同 sense 候选时必须优先选择，否则降级待审。

## F16：窄义抢占常用义或常用词性漏出

- 表现：`deliver` 加入古旧“拯救”义，`depend` 用“信任”冒充默认义，`collect` 选择较窄的“收藏”而非同 sense 的“收集”，`focus` 把“集中”塞入名词记录却漏掉可用的动词记录，`order` 漏掉常见购买／点菜义。
- 根因：输入已有 sense 和更合适候选，但候选排序没有稳定执行“宽泛常用义优先”；Skill 也没有明确要求独立处理每个有安全常用候选的词性。
- 处理：罕见、古旧、窄义不与常用义并列凑覆盖；所有候选都缺失日常核心义时可使用受控模型兜底并标记，不能可靠生成时待审；每个有常用 sense 和安全候选的词性独立输出记录。

## F17：模型无视 Skill 中的明确反例与确定规则

- 表现：更新后的 Skill 已逐字写明 `offer(n)=提供` 不合格、相同非空 sense 最多一个片段；MiniMax M2.5 返工仍输出 `offer(n)=提供`、`receive=收到；接到`、`remain=留下；剩下`。
- 根因：不是 Harness 漏注入。返工使用的新 Skill 哈希一致、工具和其它 Skill 禁用；模型没有可靠执行显式约束。
- 处理：停止继续用 MiniMax 返工。保留失败原始输出；改由 Reasonix／DeepSeek v4 Flash 在相同 Skill 下做资格测试，未通过前不得扩大批量。

## F18：纯来源守恒造成高频核心义缺口

- 表现：`depend` 缺少“依赖／取决于”，动词 `form` 只有无法独立展示的“构”；严格来源守恒只能拒绝，网页提示覆盖明显受损。
- 根因：Kaikki 中文候选覆盖和自然度不稳定，而实验目标是可用的网页短提示，不是只复制上游中文。
- 处理：用户确认受控模型兜底。仍优先使用合格 Kaikki 中文；仅在对应词性没有合适现代简中核心义时生成 1～3 个词典式短义，独立标记来源类型、原因和未验证状态，不把它写成 Kaikki 事实。

## F19：旧 Skill 资格结果被新合同误复用

- 表现：`132–145` 在纯来源守恒合同下通过，其中 `open / plan / play` 因 translations 全空而拒绝；切换到受控模型兜底后，生产门禁仍只检查结构和成本，可能把旧结果当成新 Skill 资格证据。
- 根因：实验 attempt 没有记录实际 Skill 哈希，资格门禁没有绑定当前批准 Skill。
- 处理：后续每次调用前写入 `skill.json`；资格与生产门禁必须匹配当前 Skill SHA-256。旧批次保留为历史证据，新增 `133–137` 小资格批验证 translations 全空的生成路径。

## F20：生成短义与声明词性不自然

- 表现：`poc-133 open` 的生成名词记录为 `公开；空地`；其中“公开”不是自然的名词网页短义。
- 证据：Cambridge 英汉词典的名词 `the open` 对应“室外／户外／露天／野外”，而不是“公开”。
- 根因：结构验证只能证明生成标记和词性来自输入，不能机械判断中文短义与词性的语言自然度。
- 处理：用户决定不继续做单词级资格返工；原始错误保留为失败样例。生产阶段按最多 50 条独立留痕，但一次连续跑完全部未完成批次，最后检查全部生成项并集中返工实际错误。

## F21：50 条批次在 final JSON 前被步数上限暂停

- 表现：`181–230 attempt-0` 完成 50 条逐项推理后没有可见 final JSON，Reasonix 返回 `paused after 1 tool-call rounds (--max-steps)`；0 条结论通过。
- 根因：Harness 固定 `--max-steps 1`。保存 session 显示 Reasonix 已追加继续输出消息，但上限在第二轮前暂停执行；不是模型工具越权或 Provider 超时。
- 成本：该失败 attempt 产生 1 次请求、输入 19934 tokens、输出 11927 tokens、成本 ¥0.0387704，必须计入总账。
- 处理：受控提高到 `--max-steps 2`，不使用无限 `0`；保留 attempt-0，Phase E 自动以 attempt-1 断点重试，已通过批次不重复调用。
